1. Visão Geral do Sistema

O LIGA-LUP é uma plataforma SaaS estratégica desenvolvida sob medida para a gestão integral de Atléticas Universitárias. O sistema unifica em uma única interface a gestão financeira (caixa e DRE), logística e orçamento de eventos, loja oficial e controle de estoque por tamanho, departamento esportivo (atletas e modalidades), mídias sociais/calendário de marketing, repositório de documentos legais (GED), comunicação realtime e matriz dinâmica de permissões de acesso (RBAC).

Arquitetura de Alto Nível
O sistema é uma Single Page Application (SPA) desacoplada construída em Vanilla JavaScript nativo (ES6+ Modules injetados via escopo global `window`), CSS3 Vanilla responsivo e HTML5 sem frameworks pesados (React/Angular/Vue). O backend opera como Backend-as-a-Service (BaaS) no Supabase, tirando proveito de banco PostgreSQL 15, autenticação via JWT, chamadas REST PostgREST, WebSockets Realtime e segurança rigorosa aplicada por Triggers PL/pgSQL e RLS.
Camada Tecnologia / Padrão Papel na Aplicação
Front-End SPA Vanilla JS (ES6+), HTML5, CSS3 Custom Properties Interface rápida sem tempo de compilação, com renderização reativa client-side.
Backend BaaS Supabase (PostgreSQL 15, Auth, Realtime, REST) Persistência de dados, autenticação de sessão e canal de comunicação em tempo real.
Segurança & RBAC Triggers PL/pgSQL + Matrix 2D Dinâmica no JS Verificação de autorização com bypass executivo e validação em banco nas mutações críticas.
Hospedagem & E2E Vercel Static Host + Microsoft Playwright Deploy contínuo sem servidor e suíte completa de regressão automatizada (13 testes E2E).

3. Fluxo Completo de Execução da Aplicação

O ciclo de vida de uma requisição do usuário na plataforma segue a sequência descrita no diagrama de sequência abaixo:

sequenceDiagram
    autonumber
    actor U as Usuário / Diretor
    participant SPA as index.html / app.js
    participant Auth as auth.js (Supabase Auth)
    participant DB as State (window.DB)
    participant REST as Supabase REST API
    participant PG as PostgreSQL Triggers

    U->>SPA: Acessa a URL da plataforma
    SPA->>Auth: Inicializa sessão (getSession)
    alt Não autenticado
        SPA-->>U: Exibe tela de Login (#login-screen)
        U->>Auth: Digita e-mail e senha + Clique em Entrar
        Auth->>REST: POST /auth/v1/token (signInWithPassword)
        REST-->>Auth: Retorna JWT + User UUID
    end
    Auth->>REST: Busca registro em public.usuarios + usuario_diretorias
    REST-->>Auth: Retorna usuário e diretorias vinculadas (diretorias_ids[])
    Auth->>SPA: Define window.currentUser e chama onLogin()
    SPA->>REST: Executa window.syncDBFromSupabase() [Fetch paralelo de tabelas]
    REST-->>SPA: Retorna tabelas em JSON
    SPA->>DB: Hydrata estado global window.DB
    SPA->>SPA: Invocação dos inicializadores (initUserAccess, initFinance, etc.)
    SPA->>SPA: Executa applyNavPermissions() e applyReadonlyMode()
    SPA-->>U: Exibe Painel Principal (#app-wrapper) com abas autorizadas

    U->>SPA: Executa Ação Crítica (ex: Aprovar Orçamento de Evento)
    SPA->>SPA: Checagem local canWrite('aprovar_evento')
    alt Bloqueado no Client-Side
        SPA-->>U: Exibe banner "Modo Somente Leitura" ou impede ação
    else Permitido no Client-Side
        SPA->>REST: UPDATE public.eventos SET status_aprovacao = 'Aprovado'
        REST->>PG: Dispara Trigger fn_trg_verificar_aprovacao_evento()
        alt Usuário não autorizado no Banco
            PG-->>REST: RAISE EXCEPTION 'Erro 403: Usuário sem permissão'
            REST-->>SPA: Retorna erro 42501 (Forbidden)
            SPA-->>U: Exibe modal amigável de Alerta de Segurança
        else Autorizado no Banco
            PG->>PG: Atualiza status e gera débito automático em lancamentos_financeiros
            PG-->>REST: Sucesso 200 OK
            REST-->>SPA: Confirmação da transação
            SPA->>DB: Atualiza registro em window.DB e re-renderiza UI
            SPA-->>U: Exibe notificação de sucesso
        end
    end

As modificações críticas são protegidas no banco de dados por triggers PL/pgSQL que realizam consultas relacionais e executam o bypass executivo:

-- Trigger de Aprovação de Orçamento de Eventos
CREATE OR REPLACE FUNCTION fn_trg_verificar_aprovacao_evento()
RETURNS TRIGGER AS $$
DECLARE
    v_user_cargo tipo_cargo;
    v_user_diretoria TEXT;
    v_user_id TEXT;
    v_has_permission BOOLEAN := FALSE;
BEGIN
    v_user_id := COALESCE(NULLIF(auth.uid()::text, ''), NULLIF(current_setting('app.current_user_id', true), ''));

    IF NEW.status_aprovacao = 'Aprovado' AND OLD.status_aprovacao = 'Aguardando Tesouraria' THEN
        SELECT u.cargo, d.nome INTO v_user_cargo, v_user_diretoria 
        FROM public.usuarios u LEFT JOIN public.diretorias d ON u.diretoria_id = d.id
        WHERE u.id::text = v_user_id AND u.status = TRUE;

        -- Bypass Executivo (Master, Presidente, Vice)
        IF (v_user_cargo IN ('Master', 'Presidente') OR v_user_diretoria IN ('Presidência', 'Vice-Presidência')) THEN
            v_has_permission := TRUE;
        ELSE
            -- Consulta Relacional Dinâmica (Primária + Secundárias)
            SELECT EXISTS (
                SELECT 1 FROM public.permissoes p
                WHERE p.concedida = TRUE AND p.acao_sistema IN ('aprovar_evento', 'mod-financeiro', 'mod-eventos')
                  AND p.diretoria_id IN (
                      SELECT u.diretoria_id FROM public.usuarios u WHERE u.id::text = v_user_id
                      UNION
                      SELECT ud.diretoria_id FROM public.usuario_diretorias ud WHERE ud.usuario_id::text = v_user_id
                  )
            ) INTO v_has_permission;
        END IF;

        IF NOT v_has_permission THEN
            RAISE EXCEPTION 'Erro 403: Usuário não possui permissão para aprovar eventos.' USING ERRCODE = '42501';
        END IF;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

8. Estado Global em Memória & Regras RBAC

A aplicação mantém um cache em memória no escopo global para garantir tempo de resposta instantâneo (< 5ms) nas operações da interface:

Objeto window.DB
Populado na carga inicial por syncDBFromSupabase(). Contém cópias locais em array de todas as tabelas sincronizadas (`usuarios`, `diretorias`, `usuario_diretorias`, `permissoes`, `eventos`, `lancamentos_financeiros`, etc.).
Objeto window.currentUser
Armazena o perfil do usuário logado contendo o vetor diretorias_ids[], resultante da união entre sua diretoria primária (`diretoria_id`) e diretorias secundárias atreladas na tabela `usuario_diretorias`.
9. Detalhamento dos Arquivos Críticos
app.js (Orquestrador da SPA)

Contém 132 KB de lógica central. Responsável por instanciar window.DB_Engine com métodos CRUD genéricos, executar syncDBFromSupabase() em paralelo para carregar tabelas do Supabase, gerenciar a navegação por abas com switchModule(moduleId) e delegar para os inicializadores dos módulos.

user_access.js (Motor RBAC)

Implementa a verificação canWrite(moduleId). Promove a checagem dinâmica contra o array `currentUser.diretorias_ids[]` e a matriz `window.DB.permissoes`, oferecendo bypass zero-priority para o Núcleo Executivo (`isExecutiveAdmin`). Controla a injeção do banner de visualização somente leitura (`applyReadonlyMode`).

config.js (Matriz 2D Sticky)

Contém o mapeamento CATEGORIAS_PERMISSOES abrangendo 29 ações operacionais organizadas por módulo. Constrói a tabela 2D com rolagem fixada nos dois eixos (sticky top/left) e sincroniza mutações na tabela `public.permissoes` do Supabase via togglePermissao().

11. Débito Técnico & Recomendações de Melhoria
Débitos Técnicos Encontrados
  • Arquivos Órfãos: O arquivo permissoes.sql na raiz é um snippet antigo de 4 linhas que foi superado pelos scripts da pasta database/.
  • Variáveis em env.js: A chave pública anon do Supabase está exposta no `env.js`. Embora seja uma chave pública projetada para o cliente, recomenda-se a substituição por variáveis injetadas no deploy Vercel em ambientes corporativos rígidos.
Melhorias Recomendadas
  • Migração para ES Modules & Vite: Converter os arquivos com injeção em `window.*` para escopo de módulos ES6 nativos (`import/export`) usando Vite como empacotador.
  • Paginação Server-Side: Adicionar paginação remota (limit/offset) nas consultas REST de histórico de mensagens de chat e lançamentos do livro caixa ao ultrapassar 10.000 registros.
